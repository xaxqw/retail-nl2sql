# 零售经营数据智能问数系统（NL2SQL / ChatBI）

用中文提问，系统自动生成 SQL、执行查询并给出业务结论。全流程本地私有化：本地模型 + 本地数据库，不依赖任何云服务。

## 问题背景

业务方想拿一个数，通常要走「提需求 → 数据组排期 → 出报表」，一次 2-3 天。本系统把这条链路压缩成一次提问，平均 3-5 秒返回结果。

## 数据集

自建零售经营数据集，星型模型 4 个维表 + 2 个事实表：

| 表 | 说明 | 行数 |
|---|---|---|
| `fact_order` | 订单事实表 | 499,984 |
| `fact_refund` | 退款事实表 | 29,778 |
| `dim_product` | 商品维表（10 品类 / 400 SKU） | 400 |
| `dim_customer` | 客户维表（5 大区 / 4 分层） | 50,000 |
| `dim_channel` | 渠道维表（天猫 / 京东 / 抖音 / 自营） | 4 |
| `dim_date` | 日期维表（含大促标记） | 822 |

覆盖 24 个月，GMV 2.28 亿，综合毛利率 21.2%，客单价 456.9 元。

数据里注入了 5 条真实业务规律，用于验证系统能否查出来：大促峰值、品类退货率分化、渠道客单价梯度、渠道品类偏好、客户分层金字塔。造数脚本见 `scripts/gen_data.py`，验证脚本见 `scripts/verify_data.py`。

## 上传文件直接分析

除内置零售库外，可上传任意 CSV / Excel 变成可查询的数据集：

- 拖文件到页面任意位置，或点「上传 CSV / Excel」
- 自动推断列类型（INTEGER / REAL / TEXT）、清洗列名、生成建表语句
- **每列带上真实样例值写进提示词** —— 上传数据没有人工维护的字段说明，模型只能靠样例值猜字段含义
- 上传数据集与内置库完全隔离，顶部可切换，同名文件也不会串

**xlsx 是零依赖解析的**：xlsx 本质是 zip + XML，用 `zipfile` + `ElementTree` 手写实现了 sharedStrings 字符串池解析与单元格坐标还原，没有引入 pandas / openpyxl。

限制：单文件 20 MB、20 万行以内；不支持旧版 `.xls`（需在 Excel 里另存为 xlsx）。

实测（12 行 6 列的城市销售数据，4 个问题全对），其中两条暴露过真实缺陷：

| 问题 | 修复前的错 | 修复后 |
|---|---|---|
| 哪个负责人订单数最多 | `ORDER BY COUNT(订单数)` 数的是行数，选出赵敏（错） | `SUM("订单数")`，选出李娜 11,620（对） |
| 上海和北京的销售额差多少 | `GROUP BY 城市` 后取第一行，得到上海自己的销售额（错） | 条件聚合相减，得 64.4 万（对） |

这两个错都是「SQL 能执行、结果是错的」，也说明了为什么只用 `status == ok` 判断准确率不够。

## 处理链路

```
用户提问 → 生成 SQL → 安全校验 → 执行查询 → 结果解释
                ↑____________|  （执行报错时回灌重试）
```

## 设计要点

### 1. 四层安全防护

生成 SQL 这件事本身有风险，模型可能写出 `DELETE` 或被诱导越权。四层拦截：

1. **连接层**：SQLite 以 `mode=ro` 只读方式打开，物理上不可能写入
2. **语句层**：只允许 `SELECT` / `WITH` 开头，拦截 `INSERT/UPDATE/DELETE/DROP/ALTER/PRAGMA` 等关键字，拒绝多语句
3. **表级**：`FROM` / `JOIN` 后的表名必须在白名单内，模型凭空编造的表会被拦下
4. **行级**：查询自动补 `LIMIT`，避免把 50 万行拉进内存

### 2. 生成—执行—纠错闭环

SQL 第一次执行失败（字段名写错、聚合用法不对）时，把数据库返回的报错原文回灌给模型，要求它重新生成。这是准确率提升最明显的一步。

### 3. 业务口径统一定义

同一个指标不同人算法不同，会让"客单价"每次问出不同答案。系统把 10 个常用口径固化进提示词（销售额排除取消单、客单价用去重订单数做分母、退货率分母含全部状态等），并明确要求模型不得就这些算法反问用户。

### 4. 相对时间预计算

"上个月""最近 30 天"这类说法如果留给模型推断，它会反问"是哪个月"。系统在拼接提示词时，按数据最新日期预先算成绝对区间（`上个月 = 2026-09-01 至 2026-09-30`），模型只需照抄。

### 5. 零依赖运行

核心链路（`app/` + `server.py` + `static/index.html`）只用 Python 标准库，不需要 pip 安装任何包。`app/main.py` 是 FastAPI 版本，用于对接生产环境。

## Windows 一键启动

`run.bat` 会依次：检查 Ollama 是否在跑 → 启动查询服务 → 打开浏览器。桌面快捷方式「零售问数系统」指向它。

脚本第一件事是探测 `8000` 端口是否已有实例，有就直接开浏览器，不重复启动。这一条很关键——早期版本允许重复双击，结果多个进程同时监听同一端口，页面表现为"打不开"或连接被重置。

`run.bat` 里的 Python 路径与项目路径是写死的，换机器需要改这两处。

## 快速开始

```bash
# 1. 生成数据（约 16 秒）
python scripts/gen_data.py

# 2. 确认本地模型就绪
ollama list          # 需要 qwen2.5:7b
ollama serve

# 3. 命令行提问
python cli.py "上个月各渠道的销售额分别是多少"

# 4. 启动 Web 界面（零依赖）
python server.py
# 浏览器打开 http://127.0.0.1:8000

# 5. 跑测试集
python eval.py
```

生产部署用 FastAPI：

```bash
pip install fastapi uvicorn
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 测试集设计

40 条分四类，覆盖不同失败模式：

| 类别 | 条数 | 考察点 |
|---|---|---|
| T1 单表直答 | 15 | 基础能力，答不对说明 schema 描述或提示词有问题 |
| T2 多表关联 | 10 | JOIN 关系理解、条件聚合、去重除法 |
| T3 口径模糊 | 8 | 未指定时间或指标时能否给出合理默认，而不是反问 |
| T4 应拒答 | 7 | 会不会编造。写操作、隐私、不存在的字段都该拒绝 |

## 实测结果

40 条测试集，`python eval.py --fast`（跳过结果解释，只测 SQL 生成与执行）：

| 类别 | 条数 | 通过 | 准确率 |
|---|---|---|---|
| T1 单表直答 | 15 | 13 | 86.7% |
| T2 多表关联 | 10 | 10 | 100% |
| T3 口径模糊 | 8 | 7 | 87.5% |
| T4 应拒答 | 7 | 7 | 100% |
| **总体** | **40** | **37** | **92.5%** |

延迟：平均 2.67 s，P95 5.00 s，全量总耗时 106.8 s。

三条失败全部是「过度澄清」——问题本身可答，模型却反问：

- `最近的订单是哪一天` → 反问时间范围（应当直接取 MAX）
- `退款原因一共有几类` → 反问统计口径（应当直接 DISTINCT COUNT）
- `客户质量怎么样` → 这条反问其实合理，是测试集期望标注过严，算标注问题

这暴露了 7B 模型的保守倾向：宁可不答，也不愿猜错。对客户交付来说这是可接受的偏差（答错比不答更糟），但要解决得靠更强的模型或更细的 few-shot。

明细见 `tests/result_*.csv`。

## 性能

硬件：RTX 4050 Laptop 6 GB / 16 GB RAM，模型 `qwen2.5:7b` Q4_K_M。

### 先定位瓶颈再动手

拆开测每一段，结论和直觉不一样：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 生成 SQL（LLM） | 3063 ms | 96% |
| 结果解释（第二次 LLM） | 1226 ms | — |
| SQL 执行（SQLite） | 11.3 ms | 0.4% |

**数据库根本不是瓶颈**。另外连问三次相同问题耗时一模一样（3041 / 3038 / 3068 ms），说明 KV cache 没复用，每次都要重新处理 2458 token 的提示词。

### 五项优化与效果

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 首次提问（未命中） | 4672 ms | 3466 ms |
| 重复提问（精确命中） | 4672 ms | **0 ms** |
| 近似提问（语义命中） | 4672 ms | **158 ms** |
| 单表简单查询 | 2100 ms | 1032 ms |

1. **结论模板化**：第二次 LLM 调用只为把一张表翻成一句话，代价 1226 ms 且会算错百分比。改成按结果形状（单值 / 单行 / 排行 / 时间序列）套模板，降到毫秒级
2. **两级缓存**：L1 精确匹配 0 开销；L2 语义匹配用 bge-m3 算余弦（194 ms），阈值 0.93
3. **时间口径校验**：语义缓存有个坑——「上个月销售额」和「本月销售额」相似度能到 0.95 以上，会误命中。所以命中前还要比对时间标记，把「上月 / 上个月」这类同义说法归一到同一标记，口径不同直接放弃命中
4. **keep_alive = 30m**：模型冷加载要 55 秒，不能让它被卸载
5. **启动预热**：embedding 和主模型都在后台线程预热，不让第一个真实请求承担加载成本

### 容量评估（压测）

`python bench.py 1 3 5`，每轮 10 个不同问题、关闭缓存：

| 并发 | QPS | P50 | P95 |
|---|---|---|---|
| 1 | 0.29 | 3583 ms | 3749 ms |
| 3 | 0.35 | 8323 ms | 10388 ms |
| 5 | 0.35 | 13206 ms | 15026 ms |

**并发从 1 提到 5，QPS 只涨 21%，P95 涨了 4 倍。** 单模型实例下并发不提吞吐，只是把请求排到队里——Ollama 是串行推理。

要真正提 QPS 只有两条路：把缓存命中率做上去（命中走 0 ms，不占推理资源），或者多实例 / 多模型并行。这是容量规划的依据，不是拍脑袋说「支持高并发」。

### 模型路由与降级

同一批 8 个问题的对照测试（`bench_sql_models.py`）：

| 模型 | 平均耗时 | SQL 关键点命中 | 可执行 |
|---|---|---|---|
| `qwen2.5:7b` | 2606 ms | 18/18 | 8/8 |
| `qwen2.5-coder:3b` | **980 ms** | 18/18 | **6/8** |

3b 快 2.7 倍，SQL 结构完全正确（关键点全部命中），但 8 题里有 2 题执行失败——「趋势」和「分布」这两类需要多表聚合的题写错了。

所以不做一刀切，按题型分流：

- 命中复杂信号（趋势 / 分布 / 比率 / 对比 / 排名 / 差多少）→ 直接走 7b
- 其余问题 → 先走 3b，**执行失败自动降级到 7b 重试一次**（不是把报错甩给用户）

实测分流效果：简单题平均 **1000 ms**（原 2606 ms），复杂题 3976 ms，全部返回正确结果。

**一个副作用值得记下**：两个模型交替使用会互相挤出显存，7b 从 2606 ms 涨到 3976 ms。所以路由的收益在「同一类问题连续问」时最大，混合提问时切换开销会吃掉一部分。想彻底解决得加显存（≥12 GB 才能同时驻留），或者干脆只用 3b + 更强的 few-shot。

### 被否决的优化

**`qwen3:4b-fast`**：生成速度是 7b 的两倍（56.9 vs 28.6 token/s），但关掉 thinking 后它会把思考过程当正文输出（"首先，用户的问题是…"），对多表句式遵从性差，不能用。

**`qwen3:8b`**：在 6 GB 显存上严重溢出，prefill 要 22 秒、生成 5.7 token/s，直接淘汰。

**云端 API（Groq / DeepSeek）**：速度能提升一个量级（Groq 的 Llama 70B 可以到数百 token/s），但需要 API key，且数据要出内网。对本地演示没有必要，对生产环境是首选——`app/config.py` 里改 `MODEL` 和 `OLLAMA_URL` 就能切，`llm.py` 已经把调用层封装好了。

## 迭代记录

调试过程中修掉的几个真实问题，比最终数字更能说明系统怎么工作：

1. **模型把「上个月」当成歧义**，反问用户是哪个月 → 加入相对时间预计算，直接给出绝对区间
2. **模型输出全角冒号 `CLARIFY：`**，解析器只认半角，导致澄清被误判成解析失败 → 正则兼容全角
3. **过度澄清**：问「退货率最高的五个品类」时模型反问"按什么口径算" → 把口径写死并明确禁止就算法反问
4. **模型幻觉出 `dim_region` 表**（大区实际是 `dim_customer.region` 字段）→ 被安全层表白名单拦下；同时在提示词里补了字段位置说明和 3 条 few-shot 示例
5. **few-shot 前后对比**：同一组三个问题，加示例前 0/3 通过（两条被误判为澄清、一条撞安全拦截），加示例后 3/3 通过

## 已知限制

- 7B 本地模型在复杂嵌套查询（多层子查询、窗口函数）上仍不稳定，这类问题当前会失败或需要重试
- 没有做查询结果的可视化推荐（折线/柱状自动选型）
- 表结构变更后需要重新生成 schema 描述，尚未做缓存失效机制
- 单实例部署，未做多副本负载均衡；并发能力受限于单模型推理速度
- 语义缓存没有做失效策略，数据更新后会返回旧结果

## 模型选型说明

本地环境为 6GB 显存，可用模型受限。当前主模型 `qwen2.5:7b`，生成 SQL 平均 3-5 秒。若要提升复杂查询准确率，可切换到云端大模型 —— `app/config.py` 里的 `MODEL` 与 `OLLAMA_URL` 是唯一改动点，`llm.py` 已封装调用层。
